Architecture & State Management

📦 State Caching & Late Joiner Sync

When a user joins a live broadcast minutes or hours after it starts, they must instantly see the full room state—including active co-hosts, coin scores, and camera/mic mute states—without waiting for new live events.

⚡ Redis-Backed RoomState

The Go backend maintains an authoritative RoomState snapshot in Redis (room:{room_id}:state) with a 24-hour TTL. Every room creation, viewer join/leave, seat change, and mute toggle updates this centralized cache.

🪙 Atomic Gift Score Registry

Host gift scores are recorded using atomic Redis INCRBY operations (room:{room_id}:score). In-memory score deltas are periodically flushed to eliminate race conditions under heavy gifting loads.

🔄 Late Joiner Synchronization Lifecycle
1
Viewer connects via WebSocket and transmits { "action": "join_room", "room_id": "..." }.
2
Server registers the client in the room and immediately queries the current RoomState from Redis / RAM cache.
3
Server pushes a dedicated room_info_sync WebSocket event directly to the new viewer with the complete snapshot payload.

SDK Developer Best Practice & Initialization Rule

When integrating the client SDK, listen for onRoomInfoSync (or room_info_sync). You MUST use this initial payload to populate the UI immediately (mount active co-host seat slots, initialize total gift coin count, and display mic/camera mute badges) before processing subsequent incremental delta events (such as viewer_update, gift_processed, or media_state_updated).
