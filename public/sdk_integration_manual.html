2

WebSocket Connection & Message Envelope

All signaling and real-time interactions flow through a single persistent WebSocket connection. Authentication is performed during the WebSocket upgrade handshake.

WS wss://{SERVER_HOST}/ws?token={JWT_TOKEN}
💡
Universal Envelope Format
The backend expects JSON messages wrapped with an action (or event) identifier and a payload object. Both naming conventions are accepted interchangeably.
Standard Client Outgoing Envelope WSMessage 
{
  "action": "<ACTION_NAME>",
  "room_id": "room-101",
  "user_id": "usr_alex_88",
  "payload": {
    // Action-specific parameters
  }
}

Room Lifecycle Management (WebSocket)

Controls starting a live broadcast, joining as viewer, leaving, and terminating the session.

Host Publish Message action: publish 
{
  "action": "publish",
  "room_id": "room-101",
  "room_name": "Gaming Championship Live",

  "payload": {
    "sdp": "v=0\r\no=- 12345 2 IN IP4 127.0.0.1\r\ns=-\r\nt=0 0\r\na=group:BUNDLE 0 1...",
    "type": "offer"
  }
}

2. Viewer Joining Room (join_room)

Viewer Join Request action: join_room 
{
  "action": "join_room",
  "room_id": "room-101",
  "user_id": "usr_bob_99",
  "payload": {
    "role": "viewer",
    "user_name": "Bob Viewer"
  }
}

3. Host Ending Room & Server Broadcast (room_closed)

Server Broadcast to All Room Members event: room_closed 
{
  "event": "room_closed",
  "room_id": "room-101",
  "user_id": "usr_alex_88",
  "payload": {
    "message": "Host has ended the live stream"
  }

4

State Caching & Late Joiner Sync (CRITICAL FOR UI)

❌ The Problem

When a viewer joins 30 minutes late, they missed past incremental WebSocket events (e.g. who joined co-host seats, who muted their camera, gifts already sent). Without a state snapshot, their UI renders empty slots.

✅ The Solution

The Go server maintains an authoritative RoomState in Redis (room:{id}:state). Immediately upon a successful join_room, the server pushes a room_info_sync event containing the complete live snapshot.

Immediate Server Push on Join event: room_info_sync 
{
  "event": "room_info_sync",
  "room_id": "room-101",
  "user_id": "usr_bob_99",
  "data": {
    "room_id": "room-101",
    "host_id": "usr_alex_88",
    "total_viewers": 1420,
    "host_score": 58200,
    "active_seats": {
      "0": "usr_alex_88",
      "1": "usr_sarah_cohost",
      "2": "usr_mike_cohost"
    },
    "media_states": {
      "usr_alex_88": {
        "muted_audio": false,
        "muted_video": false
      },
      "usr_sarah_cohost": {
        "muted_audio": true,
        "muted_video": false
      },
      "usr_mike_cohost": {
        "muted_audio": false,
        "muted_video": true
      }
    },
    "created_at": 1724742000
  }
}
⚠️
Mandatory SDK Rule
Client SDKs MUST use the room_info_sync payload to immediately construct the UI state (mount active co-hosts on seat slots, display the score, show mute icons) before processing subsequent incremental delta events.

7

Co-Hosting & Seat Management (WebRTC Renegotiation)

Co-hosts can request a seat (slots 1..7). When the Host accepts, the server performs dynamic WebRTC SDP renegotiation to inject the co-host's media stream to all connected viewers.

STEP 1
Viewer sends { "action": "seat_request", "payload": { "seat_id": "1" } }.
STEP 2
Host receives seat_request and approves via { "action": "seat_accept", "payload": { "target_user": "usr_sarah", "seat_id": "1" } }.
STEP 3
Server promotes viewer, binds track, and sends new offer to all viewers to inject the new video frame.
Host Accepting Co-Host action: seat_accept 
{
  "action": "seat_accept",
  "room_id": "room-101",
  "user_id": "usr_alex_88",
  "payload": {
    "seat_id": "1",
    "target_user": "usr_sarah_cohost"
  }
}
Seat Update Broadcast to All Room Members event: seat_updated 
{
  "event": "seat_updated",
  "room_id": "room-101",
  "payload": {
    "action": "seat_assigned",
    "seat_id": "1",
    "user_id": "usr_sarah_cohost"
  }
}

PK Battles (Cross-Room Streaming & Score Sync)

Enables two separate hosts to link their rooms in a competitive split-screen battle using SFU Cascading and Redis Pub/Sub cross-room score synchronization.

Host A Inviting Host Baction: pk_request
{
  "action": "pk_request",
  "room_id": "room-A",
  "payload": {
    "target_room_id": "room-B"
  }
}
Host B Accepting Battleaction: pk_accept
{
  "action": "pk_accept",
  "room_id": "room-B",
  "payload": {
    "target_room_id": "room-A"
  }
}
Real-time Dual Progress Bar Sync event: pk_score_update 
{
  "event": "pk_score_update",
  "room_id": "room-A",
  "payload": {
    "session_id": "room-A_room-B",
    "room_1": "room-A",
    "room_2": "room-B",
    "room_a_score": 3500,
    "room_b_score": 1200
  }
}
Host Ending PK Battle action: pk_stop 
{
  "action": "pk_stop",
  "room_id": "room-A",
  "payload": {
    "target_room_id": "room-B"
  }
}
